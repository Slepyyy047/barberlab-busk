# Сховище та адміністративний доступ

Початкові дані BARBERLAB зберігаються в SQLite. За замовчуванням база лежить у `outputs/barberlab/data/barberlab.sqlite`, а нормалізовані завантаження зображень — у `outputs/barberlab/data/uploads/`. Вміст автоматично засівається з підтверджених даних брифу лише під час першого запуску. Подальші зміни залишаються в базі після перезапуску. Для іншого постійного каталогу задайте `BARBERLAB_DATA_DIR` перед запуском. Каталог має бути на диску, який переживає перезапуски й оновлення застосунку; резервуйте весь каталог `data` разом.

Створіть адміністратора локально командою `npm run admin:create`. Введіть окреме ім’я та пароль щонайменше з 12 символів; поле пароля приховує введення. Пароль зберігається як scrypt-хеш, а повторне створення того самого облікового запису анулює його активні сесії. Публічних облікових даних за замовчуванням немає. Для автоматизованого запуску саме цієї CLI-команди можна задати обидві змінні `BARBERLAB_ADMIN_USER` та `BARBERLAB_ADMIN_PASSWORD`; пароль не друкується. Застосунок не створює й не змінює облікові дані під час імпорту або запуску.

Після `npm run dev` панель доступна на `/admin`. API використовує непрозору випадкову cookie-сесію, хеш якої зберігається в SQLite; cookie має прапорці HttpOnly і SameSite=Strict та діє 12 годин. Усі зміни вмісту й медіа перевіряють сесію, точний `Origin` і CSRF-токен у заголовку `X-CSRF-Token`. Токен прив’язаний до поточної сесії, повертається лише авторизованим запитом `/api/admin/session` і не записується в cookie чи localStorage. Для production задайте `BARBERLAB_APP_ORIGIN` з точним публічним HTTPS origin: тоді лише він дозволений для адміністративних змін. Без цієї змінної такі запити приймаються лише з loopback для локальної розробки. Трафік production має проходити через HTTPS.

Ліміти входу зберігаються в SQLite: 10 невдалих спроб на ім’я адміністратора та 100 загалом за 15 хвилин. Перевірка й оновлення лічильників відбуваються в SQLite-транзакції та діють між процесами на одному сервері, що використовують один локальний файл бази. Заголовок `X-Forwarded-For` не використовується для рішень безпеки. Для інстансів на різних серверах потрібне спільне серверне сховище, наприклад Redis або PostgreSQL; SQLite WAL не працює як спільна база через мережеву файлову систему.

`PUT /api/admin/content` приймає повний об’єкт `Content`; сервер обмежує тіло запиту навіть без `Content-Length`, перевіряє поля та обмеження перед атомарним оновленням запису. Успішне збереження інвалідує кеш сторінок Next.js. Завантаження через `POST /api/admin/upload` обмежує весь multipart-запит і файл; приймає JPG, PNG, WebP або AVIF до 8 МБ і перетворює їх на WebP шириною/висотою до 2000 px. Медіафайли доступні за `/api/media/<uuid>.webp`. Видалення через `DELETE /api/admin/upload` також прибирає посилання з галереї та портретів у базі.

Для production збережіть SQLite й медіа на одному постійному локальному томі та підключіть його як `BARBERLAB_DATA_DIR`. Платформи з ефемерною файловою системою потребують постійного диска або окремої сумісної БД і сховища файлів перед розгортанням. HTTPS має завершуватися на довіреному reverse proxy. Публічні дефолтні паролі, секрети в репозиторії та резервні копії в каталозі коду не використовуються.
